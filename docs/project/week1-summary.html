What shipped

The week-1 definition of done, reduced to the parts an operator actually touches. Each box below has a test, a CI run, a deployed trace or a device run behind it.

Protocol

Protocol v0, frozen

One envelope, one schema and 20 replayable fixtures. The OpenAPI file covers health, version, knowledge, pairing, token refresh and traces.

Gateway

WebSocket relay

Bearer token on connect, device.hello, 25 s heartbeat and 90 s timeout. Tasks route only inside a household, with a 24-hour idempotency window.

Pairing

Links and opaque tokens

A 5-minute single-use pairing session mints the device identity. Tokens are stored as SHA-256 hashes: 15-minute access, 30-day rotating refresh, reuse rejected.

Data

Postgres v0 with RLS

Ten tables, household_id and member_id on every tenant table, row-level security enabled and forced. Flyway applies V1 at boot.

Wake

FCM wake-up

Data-only, high-priority push with a 5-minute TTL and no body content. Sent only to offline devices, capped at 6 per minute, deduplicated per task.

Tasks

Route, queue, ack

task.create, ack, progress, result, error and cancel. Offline targets queue and are delivered on the next hello, within a 10-minute default deadline.

Traces

One id per hop

Ingress assigns or validates traceparent. Spans record accept, route, wake, deliver and ack. Trace lookup is household-only; logs carry no token or body.

Deploy

Render, Frankfurt

Docker on a distroless Java 21 runtime, 512 MB free plan, Postgres 16 in the same region. Health returns {"ok":true,"db":"ok"}.

Clients

Phone and PC halves

Android pairs, opens the socket, registers FCM, runs a delivered task and returns a terminal frame. The Windows App runs the loop locally and can drive the PC or the phone through a bridge; send-task.ps1 is the separate backend sender.

Fixes

Two real bugs closed

A silent 15-minute outage after token expiry, fixed by treating the E_AUTH frame as the refresh signal. A duplicate delivery on one socket, fixed by remembering what that session already sent.

PC

The backend device is a script, not the PC App. The Windows App runs the loop locally or drives the phone through a LAN bridge; it does not open this socket.

send-task.ps1 · SendTask.java
Postgres 16 Devices, households, tasks, events, tokens and trace spans. Row-level security scopes every read to the caller's household.
FCM A data-only push wakes the phone when it is offline. It carries a task id, never the task body. The phone then reconnects and asks for the task.
What is not here yet Approvals, sync, file transfer and the operations console are later weeks. The Windows App is a local client that can drive the phone through a bridge; it is not a backend client.

One task, end to end

  1. The PC sends task.create. The gateway authenticates the token, refuses a target outside the household before writing, applies limits, and records the task plus an accept span.
  2. The gateway routes. If the target is online, the frame goes down its socket and the task is delivered. If not, it stays queued and an FCM wake is attempted.
  3. The phone acks, then runs. The runner resolves the surface, plans, executes and returns a task.result or a named error.
  4. One trace id covers every hop. Look it up with GET /v1/traces/{traceId} using the caller's own token.

Connect the Phone App

Pairing is one paste. The app stores the identity, opens the socket itself and refreshes its own token; you do not repeat this after a reboot. This is the backend route; the PC App has a separate route below.

Current test-stack values

Gateway: wss://hopa-backend-test.onrender.com/v1/gateway
Household: 8d21f337-c740-4425-b990-741f584fda85
Bootstrap token file: %TEMP%\opencode\hopa-test-bootstrap.txt

The household id changes if the database is rebuilt. The examples below use %TEMP%\hopa-bootstrap.txt as a readable placeholder for the token file.

Before you start

  • Your shell is at the repository root, the folder containing tools\scripts.
  • The app is installed (.\tools\scripts\android-device-checks.ps1 -InstallOnly after building the APK).
  • Notifications are allowed, so the app can obtain an FCM token.
  • Android's accessibility service and HOPA's own screen-access switch are on if the phone should run tasks, not only receive them.
  • USB debugging is on if you will use the adb shortcut instead of pasting by hand.
Build and install the debug APK

The installer stages the APK over a raw adb channel because host security software can refuse adb install. HyperOS still needs Install via USB enabled and one confirmation tap on the phone. 

cd apps\android
.\gradlew.bat :app:assembleDebug
cd ..\..
.\tools\scripts\android-device-checks.ps1 -InstallOnly
Build and install commands

  1. Mint a pairing link on the PC

    The bootstrap token is read from a local file and is never printed. A session is single-use and expires after five minutes. 

    # One shell per session. Never commit or paste the token itself.
$env:HOPA_BOOTSTRAP_TOKEN = (Get-Content "$env:TEMP\hopa-bootstrap.txt" -Raw).Trim()

# First device: omit -HouseholdId. An extra phone joins the existing household.
.\tools\scripts\pair-device.ps1 -HouseholdId <phone-household-id>
    Pairing command

    It prints a hopa://pair?... link and the expiry. Use the household id printed by the first device's run; a second household cannot exchange tasks with the first.

  2. Paste it into the phone

    Open Act → How HOPA acts → My computer, then Set up the bridge (or Bridge settings). The HOPA gateway card is on the My computer screen, below the bridge card. This is the only route to it in week 1.

    • Gateway address: wss://hopa-backend-test.onrender.com/v1/gateway. A whole link fills this in automatically.
    • Pairing link, or the session alone: paste all of it, or only the p= value if the address is already filled in.
    • Tap Pair. The card should move to Live and show a device id.

  3. Or hand the link to the app over adb

    Faster when the phone is attached. Quote the link inside the adb command: the link contains &, and an unquoted device shell splits it at the first ampersand, leaving the app with a link that looks unpaired. 

    $link = .\tools\scripts\pair-device.ps1 -HouseholdId <phone-household-id> -LinkOnly
adb shell "am start -n com.hopa.android/com.hopa.app.MainActivity --es hopa.backendPair '$link'"
    adb pairing command

  4. Confirm four things

    Connection: Live, a device id, an FCM token (not “waiting for a token”), and screen access on if the phone should execute. The backend records the push token on the next device.hello.

  5. Let it run

    The socket stays open in the foreground and for 30 seconds after backgrounding. After that, the gateway pushes a data-only wake. When an access token expires, the app refreshes it by itself and returns to Live.

Phone runtime, week 1
Behaviour Value What you notice
Access token 15 minutes The app refreshes on its own; no re-pair
Refresh token 30 days, rotated on use A reused refresh token is rejected
Foreground socket open Tasks arrive immediately
Background grace 30 seconds After that, an FCM wake brings the socket back
Locked phone refused with E_DEVICE Delivery and wake still work; execution does not
Screen access off refused with E_CAPABILITY The message names HOPA's screen access

Is there a QR code?

The payload exists; the camera scanner does not — yet.

The backend mints exactly what a QR code would carry, but the Android app has no scanner in week 1. In practice you paste the link into the HOPA gateway card, or send it with the adb command above.

The link the backend returns has this shape:

hopa://pair?v=1&h=<household-id>&p=<single-use-session>&u=<gateway-url>
Pairing link format
  • h is the household the new device joins.
  • p is the single-use session. It expires in five minutes and is consumed by the first claim.
  • u is the gateway the app will connect to. Without it, the app uses the address already on screen and accepts a bare session.
  • Parameter order and percent-encoding do not matter; anything that is not a recognised link or bare session is refused rather than guessed.

A future QR scanner only needs to hand this same string to the same parser. No backend change is required for that page; the gap is entirely in the Android UI.

Open the PC App

The PC App is the Windows client in apps/windows: a WPF window plus a Kotlin sidecar that runs the same loop as the other clients. It can act on the PC itself and, through a bridge, on the phone. It is not a backend client.

The sidecar must be built before the window starts

The app finds the sidecar at apps/windows/sidecar/build/install/hopa-windows-sidecar/lib. If that folder is missing, the window opens but cannot answer. Build the sidecar first.

Build and run

# 1. Kotlin sidecar: the loop and the device adapters.
cd apps\android
.\gradlew.bat -p ..\windows\sidecar installDist --no-daemon

# 2. WPF app.
cd ..\windows\Hopa.Windows
dotnet build -c Debug

# 3. Start the window.
.\bin\Debug\net8.0-windows\Hopa.Windows.exe
PC App build and run commands
  • Prerequisites: Windows 10 or 11, the .NET 8 SDK, a JDK, and the repo's Gradle wrapper.
  • If dotnet is not on PATH: run & "C:\Program Files\dotnet\dotnet.exe" build -c Debug instead.
  • First start: the window shows a chat column and a target chip at the bottom-left. The chip starts as Laptop; Settings holds the model and bridge values.
  • No model key: the sidecar uses its demo model and answers with text instead of planning actions. Add a provider key in Settings for real PC control.
Package the app for another PC

The packaging script publishes a self-contained Windows build, copies the sidecar and a jlink runtime, then writes a zip under out/windows. It needs the sidecar build and a JDK with jlink. 

.\tools\scripts\windows-package.ps1 -SkipMsi
PC App packaging command

Drop -SkipMsi only when WiX is installed. The output is out/windows/hopa-windows-0.1.0.zip.

Headless check

# One turn without clicking the window.
.\bin\Debug\net8.0-windows\Hopa.Windows.exe --turn "say hello" --out turn.txt
PC App headless check command

Verified with the current tree: exit code 0, and turn.txt receives the sidecar's answer. This proves the window, sidecar and IPC are wired; it does not touch the backend.

Connect the PC App to the backend

There is no script for this in week 1.

The PC App never opens /v1/gateway. It has no backend bearer token, no device.hello and no inbox. The only backend client that stays connected and receives tasks is the Android app; send-task.ps1 is a one-shot sender identity, not the app.

Which PC route works in week 1
Route What it uses Status
PC App → this PC The local Kotlin sidecar over stdio, then Windows UI Automation. Works. This is how you send an action to the PC.
PC App → phone HTTP bridge plus adb; the target chip says Phone. Works when the bridge is running and paired.
PC App → backend Nothing: the app has no gateway client. Not implemented.
send-task.ps1 → backend WSS as a windows device; sends one task. Works, send only. It cannot receive tasks.
Phone App → backend WSS with its paired device identity. Works.

The PC App's --pair argument pairs it to a LAN bridge, not to the backend. The bridge address and token live in the app's Settings, and the code is printed by the bridge program: 

# Bridge pairing, NOT backend pairing.
.\bin\Debug\net8.0-windows\Hopa.Windows.exe --pair http://127.0.0.1:8765 123456 pair.txt
PC App bridge pairing command

For backend sends, use the PC-as-a-backend-device section. For a backend-to-PC action, the integration does not exist yet; the PC App can only act locally or drive the phone through its bridge.

PC as a backend device

This is the script, not the PC App.

send-task.ps1 plus SendTask.java pairs a windows identity with the backend and speaks the same gateway protocol as the phone. It is a sender: it cannot receive or run a task. It does not start the PC App and it does not share the app's bridge settings. See Open the PC App for the GUI.

Before you start

  • PowerShell 5.1 or later.
  • A JDK on PATH. The sender compiles itself into %TEMP%\hopa-tools on first use; nothing to install in the repo.
  • The bootstrap token, in the same local file the phone flow uses.
  • The phone's household id if this is not the first device. Otherwise the script creates a fresh household and the two devices cannot exchange tasks.

  1. Pair the PC once

    This claims a fresh session as a windows device, says hello and stores the tokens in %TEMP%\hopa-pc-tokens.json. A pasted link or an explicit household forces a fresh pairing even if a token file already exists. 

    $env:HOPA_BOOTSTRAP_TOKEN = (Get-Content "$env:TEMP\hopa-bootstrap.txt" -Raw).Trim()

# Join the phone's household; omit -HouseholdId for a brand-new household.
.\tools\scripts\send-task.ps1 -Pair -HouseholdId <phone-household-id>

# Already paired? Re-pair without moving households:
.\tools\scripts\send-task.ps1 -Pair -Force
    PC pairing command

    Expected shape: paired device=… household=… expires=…. The tokens are never printed. The file is ACL-restricted, but it still lives in %TEMP%, so treat it as a credential.

  2. Know the expiry

    The access token lasts 15 minutes. This sender does not refresh it (the refresh token is stored for the next slice), so a send after the window fails with E_AUTH. Re-pair with -Pair -Force; it keeps the stored household unless you pass -HouseholdId or -Link.

  3. Confirm the target

    -Pair records the phone's device id when it is the only other device online. Otherwise pass -To on each send, or use the phone's id from the HOPA gateway card.

Override the backend

Both scripts read HOPA_BACKEND_URL. With it unset they use https://hopa-backend-test.onrender.com. Set it once per shell to point at a local stack: $env:HOPA_BACKEND_URL = "http://127.0.0.1:8080".

Send action to the PC

This runs on the PC itself through the PC App and its sidecar. It is local work, not a backend task, and it never leaves the machine.

A real model is required for actions

With no provider key, the sidecar uses its demo model: it answers with text and does not plan taps or launches. Add a model in Settings → Model before expecting the PC to open or type into an app.

  1. Open the PC App

    Build the sidecar and the window as shown in Open the PC App, then start Hopa.Windows.exe.

  2. Choose the Laptop target

    The chip at the bottom-left of the composer says Laptop or Phone. Click it until it says Laptop; the subtitle then reads “Running on this laptop”. Do not use the Phone target for PC work.

  3. Configure the model once

    Open Settings, pick the provider, and fill Base URL, Model name and the Model key. The key goes into Windows Credential Manager, not the repository. Save.

  4. Ask for the action

    Type a goal in the composer, for example open notepad or type hello in notepad, then press Enter or the send arrow. The sidecar observes the desktop, plans, calls Windows UI Automation, and returns the result. Payment and destructive steps ask first, with a 120-second wait.

  5. Read the refusal, not a fake success

    Elevated windows and secure screens cannot be driven by this build. The app says so instead of pretending the action ran.

Headless PC check

The app has a built-in PC-action check. It sets the target to Laptop, asks for open notepad and type hello in notepad, and writes the log. Run it only when an open Notepad is acceptable; it needs the same model key as the window. 

# Opens Notepad and types "hello", then writes the log.
.\bin\Debug\net8.0-windows\Hopa.Windows.exe --pc-check pc-check.txt

# Any other goal:
.\bin\Debug\net8.0-windows\Hopa.Windows.exe --turn "open calculator" --out turn.txt

Send action to the Phone

There are three routes to the phone. The first is the deployed backend; the other two stay on the LAN. Only the first needs a paired device on the gateway.

Ways to send an action to the phone
Route Use it when Needs
Backend → phone You want the deployed relay, wake-up and trace. This is the week-1 path. The phone paired to the gateway and send-task.ps1 on the PC.
PC App → phone You want the PC window to drive the phone's visible screen over the LAN. The bridge running, its address and token in Settings, adb, and the target chip on Phone.
Phone → phone You are already holding the phone and want the simplest run. HOPA's screen access and the This phone choice in Act.

Route 1: backend → phone

One command sends one task and waits for the terminal frame. The default timeout is 200 seconds, long enough to cover a free-plan cold start plus a wake. 

# The common case: -To comes from the pairing that discovered the phone.
.\tools\scripts\send-task.ps1 -Goal "open settings"
Basic send command 
# Explicit target and timeout.
.\tools\scripts\send-task.ps1 `
  -Goal "open settings" `
  -To <phone-device-id> `
  -TimeoutSec 200
Full send command
send-task.ps1 options
Option Use it when
-Goal Required for a send. Plain language, for example "open settings".
-To The phone was not recorded at pairing, or more than one device is online. Defaults to the stored id, then the only other device online.
-TimeoutSec The wait for task.result or task.error. Default 200.
-Pair This PC has no stored identity, or you want a fresh one. Stops after pairing.
-HouseholdId The PC must join the phone's household. Ignored with -Link.
-Link You already minted a fresh hopa://pair link. Only with -Pair.
-Name The device name shown in the household. Defaults to the computer name.
-Force Pair again despite an existing token file. Keeps the stored household unless overridden.

What you should see

The sender prints the ack first, then one terminal frame, then the trace to look up:

ack task=<uuid> trace=00-…-…-01 state=delivered
result summary="Settings is open"
trace=00-…-…-01
Example sender output
  • state=delivered means the phone's socket took the frame. It does not yet mean the task succeeded.
  • state=queued means the phone was offline. A wake was attempted; the task is delivered on the next hello, inside the deadline.
  • result summary=… is the model or stub's answer. Week 1 has no provider key on the phone, so this is the stub's text.
  • error code=… message=… is a named refusal or failure, not a timeout. Exit code 1.
  • Exit codes: 0 success; 2 no paired PC (run -Pair first); 1 any other failure.
Read the trace for that task

Send the same bearer token the device uses (read it from the token file; do not print it). The response is scoped to the caller's household, so a token from another household gets a 404. 

$tokens = Get-Content "$env:TEMP\hopa-pc-tokens.json" -Raw | ConvertFrom-Json
Invoke-RestMethod `
  -Uri "https://hopa-backend-test.onrender.com/v1/traces/<trace-id>" `
  -Headers @{ Authorization = "Bearer $($tokens.accessToken)" }
Trace lookup command

Route 2: PC App → phone over the bridge

This route keeps the run on the LAN. The PC App sends the goal to a bridge, the bridge drives the phone's visible screen with adb, and the phone does not need Android's accessibility service for it.

  1. Start the bridge

    Install the bridge once from the repo (python -m pip install -e services\bridge), put adb on PATH, then run it and keep the terminal open. It prints the address and a one-time pair code: 

    hopa-bridge --platform android bridge --host 0.0.0.0 --port 8765

# In another terminal, the phone must be listed:
adb devices
    Bridge start command

  2. Pair the phone and the app

    Pair the phone from Act → How HOPA acts → My computer with the address and pair code. Then put the same bridge address and its token in the PC App's Settings → Bridge, or pair the app from the command line: 

    # The pair code comes from the bridge console; this is not the backend.
.\bin\Debug\net8.0-windows\Hopa.Windows.exe --pair http://127.0.0.1:8765 123456 pair.txt
    Bridge pairing example

  3. Switch the target and ask

    In the PC App, click the target chip until it says Phone, then ask for the action, for example open settings. The phone's screen opens visibly. If the chip says Laptop, the app acts on the PC instead.

Full bridge setup and failure modes are in the Android run-modes guide, section 5.

Route 3: on the phone itself

Open HOPA on the phone, choose This phone in Act, and ask directly. This needs HOPA's screen-access switch and Android's accessibility service, but no PC and no backend. It is the simplest check when the phone is already in your hand.

What the phone does with a task

A delivered frame is not a remote command. The phone decides how to act, using its own How apps open setting, and the backend only sees the result.

HOPA's own “How apps open” setting
Mode What happens What it needs
auto The runner picks a surface that can work now. Screen access or the bridge, depending on the choice.
hidden Runs in the background without showing the app. Screen access; a locked phone is refused.
onscreen Brings the work to the visible screen. Android's accessibility service and HOPA's switch on.
bridge Sends the work to the paired PC over the LAN bridge. A running bridge on the same network.
  • Delivery → ack → plan → run → terminal frame. The user sees a task as it arrives; there are no approvals in week 1.
  • No provider key on the test phone. An awake run returns the stub model's answer. That proves delivery, screen resolution and the terminal frame, not model-driven taps.
  • Honest refusals. A locked phone answers E_DEVICE; screen access off answers E_CAPABILITY with instructions instead of pretending to run.
  • Background runs are noisy and quiet in the wrong places. Every background run can raise an approval-style notification even when no approval is needed, and a background result has no notification. Both are known UX defects, not protocol behaviour.

Check and fix the deployment

tools/scripts/render-check.ps1 answers the three questions the dashboard answers: is the gateway healthy, is its database reachable, and is the live commit the one on main? It wakes a sleeping free instance and can redeploy without a dashboard visit.

What it reads

  • GET /v1/health — status, version and the database state the app reports.
  • The Render API — service state, the live deploy and its commit, whether DATABASE_URL is present, and the Postgres instance.
  • The local git checkout — branch and HEAD, so “stale” means the live commit differs.

Commands

# Check, waking the service if it is asleep.
.\tools\scripts\render-check.ps1

# Redeploy only when the live commit differs from local HEAD.
.\tools\scripts\render-check.ps1 -RedeployIfStale

# Redeploy now, optionally clearing the build cache.
.\tools\scripts\render-check.ps1 -Redeploy -ClearCache

# Deploy a specific commit.
.\tools\scripts\render-check.ps1 -Redeploy -Commit <sha>

# Show what a deploy would send, without sending it.
.\tools\scripts\render-check.ps1 -RedeployIfStale -DryRun

# Health only: no Render API, no key needed.
.\tools\scripts\render-check.ps1 -NoApi -Url https://hopa-backend-test.onrender.com
Deployment check commands

The API half needs a key

Service, deploy and database checks read RENDER_API_KEY from the environment. The script never prints it. Without a key, use -NoApi and pass -Url; you still get the health check and the wake-up.

Reading the result

  • Exit 0 — the service is healthy and the database answers.
  • Exit 1 — a check failed; the lines above say which one.
  • Exit 2 — the service name or the API key could not be resolved.
  • -Json — one machine-readable object instead of the report.

The database line shows expires in N day(s) when the free Postgres instance is close to its expiry. That is a release gate, not a warning to ignore; move the web service and the database to paid plans before beta.

Troubleshooting

The failures seen while bringing up the phone and the PC, with the fix that worked.

Symptom → cause → fix
Symptom Likely cause Fix
PC fails with E_AUTH after roughly 15 minutes The PC sender does not refresh its access token. Re-pair: .\tools\scripts\send-task.ps1 -Pair -Force. It keeps the stored household.
Phone goes silent after about 15 minutes, but wake notifications still appear An old build ignored the E_AUTH frame and retried the dead token. Use a build containing the refresh fix; the app should refresh and return to Live without a re-pair.
ack state=queued, then E_DEVICE phone is locked The wake worked, but the runner refuses to execute while locked. Unlock for local execution. The delivery and wake half is already proven.
E_CAPABILITY screen control is off HOPA's screen-access switch, Android's accessibility service, or both are off. Turn both on and confirm the Screen access page says Android service: On and Connection: Live.
The phone looks unpaired after an adb launch The device shell split the link at &, so the app saw only hopa://pair?v=1. Quote the link inside the adb command, exactly as in the example above.
Pairing does nothing, or says the session is invalid The session is single-use and expires in five minutes; it may already be claimed. Mint a fresh link and paste the whole thing.
Task stays queued forever Phone offline past the deadline, wrong target id, or a different household. Check presence and household; the default deadline is 10 minutes. Re-pair both devices into one household if needed.
E_TENANT on a send The target belongs to another household. The gateway refuses before writing. Pair into the phone's household; do not create a second one by accident.
First send takes 30–60 seconds The free Render service was asleep; the first request includes a cold start. Warm /v1/health before a demo. A paid instance removes the sleep.
Screen access disappears after force-stop or reinstall HyperOS clears enabled_accessibility_services. Set it again from adb and toggle HOPA's switch off/on; a reboot is the reliable reset.
The Windows app's --pair does not reach the backend That pairing is for the LAN bridge, not the gateway. Use send-task.ps1 for backend sends; keep the Windows app for the bridge path.
dotnet is not recognized by PowerShell The .NET 8 SDK is installed but its directory is not on PATH. Use & "C:\Program Files\dotnet\dotnet.exe" build -c Debug, or add that folder to PATH.
The PC App opens but cannot answer The Kotlin sidecar was not built, or the app cannot find it. Run the sidecar installDist from Open the PC App; set HOPA_SIDECAR_LIB if it lives elsewhere.
Sidecar build fails: “Unable to delete contracts.jar” A Gradle daemon still holds the jar on Windows. Run .\gradlew.bat --stop, then retry installDist.
The PC App says “Demo model” and does nothing No model provider key is configured, so the stub only answers with text. Settings → Model: fill provider, base URL, model name and key, then save.
The PC App acts on the wrong machine The target chip is on the other device. Click the chip until it says Laptop for PC work or Phone for the bridge.
An elevated window refuses the PC action UI Automation cannot cross the elevation boundary in this build. Expected; the app reports the refusal. A signed uiAccess helper is not built yet.
