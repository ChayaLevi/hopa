How admission fits

The PC starts with no household and no account. The phone is already signed in and owns the household key. The backend is the meeting point, and it never sees the plaintext key.

  1. The PC mints a pending session.

    POST /v1/pair/pending carries the platform, name, X25519 public key and algorithm. The answer is a session id, a one-time secret, a QR string and a five-minute expiry. No household is involved yet.

  2. The phone resolves the secret.

    POST /v1/pair/pending/resolve returns the PCâ€™s name, platform, public key and fingerprint. The phone shows the fingerprint before it approves; the resolve response never names a household.

  3. The phone vouches.

    The phone wraps the household content key to the PCâ€™s public key with KeyWrap.wrapForDevice and posts the 60-byte blob to POST /v1/pair/vouch. The server parks the ciphertext on the pending row.

  4. The PC claims.

    POST /v1/pair/claim presents the same secret and public key. One transaction creates the device, moves the wrap into household_key_wraps and issues the token pair. The response carries the wrap and the voucherâ€™s public key.

  5. The PC unwraps and connects.

    The sidecar derives the same static-static secret, unwraps the 32-byte content key, stores it owner-only and opens the gateway. Incoming task bodies are {"sealed": â€¦} under that key; diagnostics stay plaintext.

What the server can see

The secretâ€™s hash, the pending deviceâ€™s public key, the wrap bytes, the household binding after a vouch, and the task metadata. It cannot read the content key, a sealed task body, or a conversation. The phone number is a login column, not a key; Lane A has no route that returns it.
