A2UI for HOPA: what it is, what we have, and how to add it

1. A2UI in simple words

A2UI lets an agent ask for a screen without sending any code. The agent sends a short JSON description, something like "a card with a title, two lines of text and two buttons". The app on the phone or PC reads that description and draws it with its own native buttons, fonts and colours.

Think of a restaurant order. The agent is the customer: it can only order dishes that are on the menu. The app is the kitchen: it cooks each dish its own way. The menu is called the catalog. If the agent orders something that isn't on the menu, the app refuses it.

It's data, not code

No HTML, no JavaScript, no iframes. A message can describe a UI but can't run anything, so it's safe to accept from a model or from another device.

Native look

The same message becomes Compose on Android, ArkUI on HarmonyOS and WinUI on Windows. Each one keeps its own theme and accessibility.

Can stream and update

The agent can send part of a card first and fill it in later, or just change the data under it (for example "the price is now ¥12").

Any transport

A2UI only defines the message shapes. They can travel over A2A, SSE, a WebSocket, or inside our gateway envelope.

A2UI is an open project that Google started (Apache-2.0, at a2ui.org and github.com/a2ui-project/a2ui). Upstream versions: v0.8 is deprecated, v0.9 is closed, v0.9.1 is a closed patch, and 1.0 is current and stable. HOPA pins 1.0 (ADR-0027, spec/a2ui/VERSION).

2. How it works, step by step

In 1.0, the version we pin, there are four messages from the agent (createSurface, updateComponents, updateDataModel, deleteSurface) and one back for a tap (action). Components are a flat list, ids are plain identifiers (no hyphens), one component must have the id root, and bindings are written {"@path": ...}. Here is roughly what a HOPA approval card looks like (shortened):

{"version":"1.0","createSurface":{"surfaceId":"appr_tsk42_1",
  "catalogId":"https://hopa.dev/contracts/a2ui/hopa-catalog.v1.json"}}
{"version":"1.0","updateComponents":{"surfaceId":"appr_tsk42_1","components":[
  {"id":"root","component":"Card","child":"col"},
  {"id":"col","component":"Column","children":["title","pay","btns"]},
  {"id":"title","component":"Text","text":"Pay for the Meituan order?"},
  {"id":"pay","component":"PaymentNotice","amount":{"@path":"/payment/amount"}},
  {"id":"btns","component":"Row","children":["deny","allow"]},
  {"id":"allow","component":"Button","child":"allowTxt","action":{"event":{"name":"approve"}}},
  ...
]}}
{"version":"1.0","updateDataModel":{"surfaceId":"appr_tsk42_1","path":"/payment","value":{"amount":"¥12.40"}}}

// back from the phone that was tapped:
{"version":"1.0","action":{"name":"approve","surfaceId":"appr_tsk42_1","sourceComponentId":"allow",
  "timestamp":"2026-11-22T10:15:00Z","context":{}}}

3. Why HOPA wants it

The backend plan already names this as a future function (docs/project/plan/backend/weekly-plan.md, "Future functions"):

"A2UI relay: Approval and choice cards as A2UI surfaces, drawn on whichever device is in hand; the tap goes back to the acting device."

Today a question can only be answered on the device that is doing the work. If the PC is running a task and needs a "yes", you have to walk to the PC. When a child's purchase needs a parent (week 5, "Family approvals"), the parent's phone has to draw a card for an action that happens on a different device. We need one neutral card format for that, which all three clients can draw and which the server never has to read. A2UI fits:

  • Three native clients. Android is Compose, HarmonyOS is ArkUI, Windows is WinUI/C#. Sharing a web view or shipping code to each is out. Data that each one draws natively fits.
  • The server must not read bodies. Bodies become ciphertext from week 2. An A2UI message is just JSON inside the encrypted body, and the server only routes it.
  • Safe by construction. A message from another device or from a model can't run code. It can only use the components in our catalog.
What A2UI must not change: golden rules 1 and 2 in CLAUDE.md. A remote tap is a signed answer. The acting device checks it, and its own ActionExecutor still runs guards → payment approval → execute → verify → record. The card is only how the question is shown. The decision is still made on the acting device.

5. What has to be built

  1. A pinned A2UI subset and a HOPA catalog in spec/: the message shapes we accept, plus a catalog of around 10 components (Text, Row, Column, Card, Button, CheckBox, Divider, Image, MultipleChoice, and our own PaymentNotice).
  2. A shared Kotlin model in core/contracts (UI-free, per golden rule 5): types, codec, a validator that rejects anything outside the catalog, and a deterministic builder from ApprovalRequest and Decision.Ask to a surface.
  3. Protocol: allow task.needs_approval and add a choice and an answer type to the gateway enum, with fixtures.
  4. Signed answers: a per-device signing key, and an answer bound to task id, surface id, action hash, nonce and expiry. The acting device verifies it before it counts as consent.
  5. An approval gateway that races local and remote: show the local sheet and publish the surface, and the first valid answer wins. A timeout still means deny.
  6. Three renderers for the HOPA catalog: Compose, ArkUI and WinUI. Each maps catalog entries to existing components so the cards look like today's sheets.
  7. Backend routing: deliver a surface to the right member's devices, expire it, close it on the others once answered, and audit it.
  8. Housekeeping: a NOTICE entry crediting A2UI (idea and format, no code copied), an ADR, and conformance fixtures shared by all clients.

6. Implementation plan

The phases are lined up with the backend weeks so nothing is built twice. Week 3 already plans "own-device approval card messages" and week 5 plans family approvals. My recommendation is to make those approval card messages A2UI from the start. Then the post-beta "A2UI relay" becomes a widening of what we already have, not a rewrite.

Phase 0: Decide and pin written, ADR proposed

Owner: lane A · before week 3 starts
  • ADR-0027, "Approval and choice cards are A2UI 1.0 surfaces" (docs/design/decisions/0027-a2ui-approval-and-choice-cards.md): the version, the subset, the catalog id, the transport inside the existing task.needs_approval and task.result bodies, and the safety rules.
  • spec/a2ui/VERSION = 1.0, plus spec/a2ui/README.md.
  • The NOTICE credit (item 6) and a row in the ADR index.
Done when: ADR-0027 is accepted and merged.

Phase 1: Spec and shared core model done

Owner: lane A · week 3
  • spec/a2ui/hopa-catalog.v1.json: Text, Row, Column, Card, Button, Divider, Icon and PaymentNotice, with allowed parents and children. It is a valid A2UI 1.0 catalog.
  • spec/a2ui/messages.schema.json: the HOPA subset of 1.0 in both directions. spec/a2ui/upstream/: the upstream 1.0 schemas at commit d4f2761b.
  • spec/fixtures/a2ui/:
    • surfaces.json: 34 cases accepted or refused with code and path, plus 8 approval-rule cases;
    • replies.json: taps and errors, plus how an answer and a choice are read;
    • builders.json: golden cards.
  • core/contracts/.../a2ui/:
    • A2uiCodec: strict decode and encode;
    • A2uiSession: surfaces for a renderer's lifetime, applied all or nothing, with the graph rules;
    • A2uiSurface: what a renderer draws, plus tap();
    • ApprovalSurfaces: build, problem and allowed;
    • ChoiceSurfaces: build and chosen.
  • 15 host tests replay the fixtures. tools/checks/check-a2ui.py runs in CI and validates every message against both our schema and upstream's.
Done: every fixture matches, refusals name a code and a JSON Pointer, and the builder output is pinned by goldens.

Phase 2: Android renderer, local only done

Owner: Android · week 3
  • apps/android/platform/ui/.../a2ui/:
    • A2uiSurfaceView: the general renderer for the HOPA catalog;
    • A2uiApprovalSheet: an approval surface drawn as today's dialog;
    • ChoiceChips: a choice surface drawn as today's chips.
  • ApprovalSheet keeps its signature but now builds a card with ApprovalSurfaces and runs it through the full codec and A2uiSession. Allow is only an approve tap on this surface. A card that fails a check is denied.
  • ChatScreen draws its chips from a choice surface, and a tap is read back with ChoiceSurfaces.chosen.
  • Goldens were recorded from the old code first. The new rendering matches all five pixel for pixel: three sheets, the acknowledged payment sheet, and the chips. Two new tests cover the generic view and the deny when a card can't be built.
Done: nothing changes for the user, and the goldens and approval behaviour tests pass.

Phase 3: The card on the existing PC → phone relay code done

Owner: lane A + Android + Windows · week 3 → 4

The relay itself already worked (#144, #158): the PC sends task.needs_approval, the phone's RemoteApprovalRunner shows the sheet, and the answer comes back as task.result. This phase put the A2UI card and its answer on that path. It built no new transport.

  • No new envelope types for approvals (ADR-0027). The task.needs_approval body gains an a2ui array next to the typed approval. The task.result answer gains approval.action, or approval.error when a card was refused. All of it stays inside the encrypted body.
  • Sidecar (Kotlin): HostApproval gives each question its own surface id, unique across restarts, and builds the card with ApprovalSurfaces.wire. Protocol.approvalRequest carries it to the window as an a2ui field.
  • Window (C#): ApprovalRouter copies a2ui unchanged into the phone's body, and passes the phone's approval.action back to the sidecar in approval.result. The C# side never judges a card.
  • The check exists once: HostApproval.resolve runs ApprovalSurfaces.answered(allow, action, surfaceId). A mismatched, malformed or wrong-surface tap is deny. There is no C# port of the rule.
  • Phone (Android): RemoteApprovalRunner checks the sent card with ApprovalSurfaces.receive and draws it as sent. The checks run in order: the A2UI rules, problem(), then matches(), which confirms the card shows the typed request (option C, ADR-0027 section 5). A card that fails is never drawn: the answer is deny with the A2UI error. With a card, allow counts only with that card's approve tap, which goes back as approval.action. A frame without a2ui keeps the old path, so old PCs keep working.
  • UiApprovalGateway.ask(request, card) puts the checked card on the one sheet, and ApprovalSheet draws it in place of a locally built one. Timeouts are unchanged: phone 90 s < window 100 s < sidecar 120 s, and every one of them means deny.
  • Shared fixtures for every client: surfaces.json receivedCases (23 cards shown or refused, with the reason) and replies.json wireAnswers (8 answers as task.result carries them).
  • Deferred: the capability gate in device.hello. The gateway doesn't yet tell the PC what the phone advertised, so the card is always attached, and an old phone ignores it. Moved to Phase 6: backend expiry and closing the card on the other devices, which only matters once there is more than one answering device, and the Android RemoteApprovalGateway for the reverse direction (the phone acts and asks).
Code done and tested: 7 contract fixture tests, 6 phone runner tests, 6 sidecar tests and 2 window tests cover a matching tap, a deny tap, a tap for another surface, a malformed tap, a card that shows another amount, a card that is not valid A2UI, and an old client on either side. Still to do: the end-to-end demo, where a PC task asks and the phone answers, and its trace showing needs_approval → answer → result.

Phase 4: Signed answers code done

Owner: lane A + Android + Windows · week 4 → 5 · ADR-0028

Decided: keys are pinned on first use. The phone and PC never talk directly (each pairs with the server), and bodies are not sealed yet, so a key handed out by the server would not stop a forged answer.

  • Each question carries a challenge (task.needs_approval challenge): a fresh 16-byte nonce and the asker's deadline. The sidecar creates it, and the window copies the whole relay (card and challenge) to the phone unchanged.
  • Each answer is signed (body.approval.signature): Ed25519 over length-prefixed fields: the nonce, the deadline, the card's surface id, a hash of the request's title, body, amount, merchant, consequence, payment flag and action, and the decision. The phone's key is created on its first answer and kept in the encrypted settings store (ApprovalSigner).
  • The PC checks every phone allow (AnswerCheck in core/backend, run by HostApproval). The first verified key per phone is pinned in phone-keys.json, and later allows need that key. Deny for: a changed amount, another card, a replayed answer, a late answer, a deny presented as allow, another key, an unsigned answer from a phone that signs, and a broken pin file. Phones from before signing keep working until they sign once.
  • Compare and reset: the PC logs the fingerprint it pins, and the phone shows its fingerprint on the gateway card in Settings. After pairing a phone again, hopa-sidecar --forget-phone-key lets the new key pin.
  • Shared vectors: spec/fixtures/approval-signatures.json (3 signature vectors and 15 answer checks), generated in Python by tools/scripts/build-approval-signature-fixtures.py, independently of the Kotlin code, which reproduces it byte for byte.
  • Not in this phase: who may answer (role checks are Phase 6), a key directory the whole household can verify, a settings button to forget a key on Windows (Phase 5), and the stronger direct "link this PC" key exchange.
Code done and tested: a tampered, replayed, late or re-keyed answer can't approve anything (core/backend fixtures, sidecar HostApprovalTest, phone RemoteApprovalRunnerTest). Still to do: the end-to-end run on a paired phone and PC, checking that both screens show the same fingerprint.

Phase 5: Windows and HarmonyOS renderers (4–6 days, can run in parallel)

Owner: Windows · HarmonyOS · weeks 4–5
  • Windows: the card already reaches the window inside approval.request (Phase 3), so no new stdio event is needed. Hopa.Windows gets a XAML renderer for the HOPA catalog that replaces Dialogs/ApprovalWindow. ApprovalRouter still decides who answers, and its automation override keeps answering without a card. Headless stays DenyAllApproval.
  • HarmonyOS: an ArkTS port of the validator (or codegen from the schema), plus an ArkUI SurfaceView used by ApprovalSheet.ets and the laptop's ChatRail.
  • All three clients run the same spec/fixtures/a2ui suite.
Done when: the same fixture renders on all three and returns the same action JSON.

Phase 6: Family approvals over A2UI (week 5, Gate 2)

Owner: lane A + B
  • Routing by role: a child's payment surface goes to the parents' devices, and an elder's goes to the caregiver, by consent.
  • Backend TaskRouter (moved from Phase 3): expire a card at its deadline, and close it on the other devices when one answers. Sending a choice card across devices needs a new envelope type, which gets its own decision.
  • Advertise and honour a2uiRendererCapabilities in device.hello once the gateway shares it between devices.
  • RemoteApprovalGateway (Android, moved from Phase 3): wraps UiApprovalGateway so a phone that acts can publish its card to other devices and take the first valid answer.
  • The card shows who asked and from which device. That text comes from the builder, never from the model.
  • Audit row per surface: shown, answered by, signed, verified, outcome. Reminder push before expiry.
Done when: Gate 2 passes. A child's task is approved on a parent's phone, with the signed answer verified on the child's device and an audit trail.

Phase 7 (after beta): Wider A2UI

Optional
  • Richer result cards (a list of found files, a draft email with an "edit" field) in the chat.

7. Risks and open questions

Rule: the model never writes an approval card. If the LLM could make the layout, it could put "Allow" where "Deny" belongs, or hide the amount. Approval and payment surfaces are built only by deterministic code from ApprovalRequest. The validator on the receiving device rejects an approval surface that lacks the required parts (amount, merchant, consequence, both buttons).
  • The spec will keep moving. 1.0 is stable, but later versions will come. Mitigation: pin the version, keep our subset small, and wrap it behind our own types so a rename touches one codec.
  • We write three renderers. There's no official Compose, ArkUI or WinUI renderer. Mitigation: a small catalog (around 10 components) and a shared fixture suite.
  • The payment gate. A remote "yes" is input, not permission. The acting device still decides, and when it's unsure it denies. Never add a "trust remote" flag (golden rule 2).
  • Encryption timing. Surfaces carry amounts and merchants, so they must ride in the encrypted body. If week 2 encryption slips, cross-device surfaces wait for it.
  • Two answers at once. When the phone and PC both tap, the first valid signed answer wins. The acting device closes the others with a delete-surface message, and late answers are ignored.
  • Settled (ADR-0027): a receiver draws the card it was sent, after checking that it shows the typed request (option C). Rebuilding and comparing was rejected, because every wording change would break older receivers.
  • Settled (ADR-0027): approvals reuse task.needs_approval and task.result, with no new envelope types. Still open: the envelope type for sending a choice card to another device.
  • 1.0 is wider than we need: it adds function calls, multiple catalogs and templates. Our receivers refuse everything outside the HOPA subset, so a newer sender can't widen what we draw.
  • Open: should HarmonyOS reuse the Kotlin core through codegen from the JSON schema, or keep a hand-written ArkTS port with the shared fixtures as the check?
