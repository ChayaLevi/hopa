# catalog - what HOPA can open, and which app answers

The app catalogue, the approval vocabulary and the prompt rules - mostly
generated from `spec/` - plus the router that walks them to pick a target for a
goal.

## Packages, bottom first

| package | what lives here | depends on |
|---|---|---|
| `data` | `Catalog`, `CatalogApp`, `CatalogSite`, `CatalogTarget`, `ApprovalPolicyData`, `PromptRule`: the tables themselves | - |
| `knowledge` | `Knowledge`, `KnowledgeBundle`, `KnowledgeCodec`, `KnowledgeSource`, `FileKnowledgeStore`: the bundle and the store that can replace it | data |
| `routing` | `AppRouter`, `CatalogRoutes`, `RouteMatch`, `RouterHint`, `RouteTarget`: the goal to a package | contracts, data, knowledge |

## Rules

1. **Generated means generated.** Files under `data` start with `// Generated by`.
   Edit `spec/`, run `tools/scripts/build-*.py`, commit; `--check` in CI fails on
   a stale commit.
2. **No ktlint in this module.** Reformatting generated output would break
   `--check`, so the whole module stays out of it.
3. **The approval table is bundled, never downloaded.** A fetched catalogue may
   say which app to open; it must not be able to make the gate less careful.
4. **Routing reads, it does not know.** `AppRouter` only walks the catalogue it is
   given; a new app is a data change, not a code change.
5. **No Android, no network.**

## Tests

```
./gradlew :catalog:test :catalog:check
```

`CatalogRoutesInstalledTest` replays `spec/fixtures/routing.json`, so the router is
checked against the same fixtures as every other client.
